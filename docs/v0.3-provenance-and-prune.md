# v0.3 design: provenance model and `--prune`

Joint design decision (orchestrator + gpt-5.6-sol adversarial consult, 2026-07-17). The
consult **vetoed** the first-draft designs for provenance, `--prune`, and the Codex
project layer, and **accepted** the `enabled_tools` item. This is the design that shipped.

## Why a provenance model

`--prune` was deliberately withheld in v0.2. The blocker: config discovery kept only the
*winning* server per name and discarded shadowed lower-precedence entries, so it could not
answer "if I delete this server, does a lower-precedence one reactivate?" Deleting a
project-scope winner can bring back a user-scope server of the same name, so a naive
"tokens saved = this server's definition cost" is wrong.

## The honesty problem the consult surfaced

Two failures made a naive `--prune` unsafe:

1. **Usage is not project-attributed.** Transcripts are windowed home-wide; the Codex
   adapter reads `session_meta` but never records a session's `cwd`. A project-scope
   server can therefore show "0 calls, measured" purely because the window is full of
   sessions from *other* projects where that server was never configured. Calling that
   `prune` is a false positive.
2. **`~N` is an estimate, not a bound.** The `chars/4` heuristic carries roughly +/-25%
   error, and a reactivated server may cost *more* than the one removed. "Save up to ~N"
   reads as a guarantee it cannot make.

## What shipped

### Provenance (internal)

- `ServerConfig` gains `precedence: int` (default `0`, assigned per scope) and
  `shadowed: tuple[ServerConfig, ...]` (immutable default `()`), the same-name
  lower-precedence entries this winner overrides, highest precedence first.
- `_merge_servers` is precedence-aware: an incoming entry of *strictly higher* precedence
  shadows the existing one and inherits its chain; an *equal*-precedence collision (e.g.
  two `projects` keys normalizing to the same path) keeps the last and warns but is **not**
  recorded as a shadow, so it never looks like a reactivation.
- Raw `ServerConfig` is never serialized (its `env`/`args` can hold secrets). JSON is
  built only from `ServerRow` and the safe `PruneSuggestion`.

### Prune classification (`engine.build_cli_report`, always computed)

A `PruneSuggestion` is emitted for each `prune`-verdict row with a *measured, non-zero*
definition cost, in one of two tiers:

- **`suggestion`** (clean net saving): scope is `user` (global, active in every session,
  and — being lowest precedence — shadows nothing), and provenance is complete. Estimated
  net saving = the winner's measured definition cost.
- **`candidate`** (needs review): everything else. `net_tokens` is `null`; the reasons
  list explains why — non-global scope (usage not project-attributed in v0.3), an enabled
  shadow that would reactivate (`reactivates` names it), or an unparsed config layer.

A *disabled* immediate shadow is not a reactivation: that disabled entry would become the
winner, launch nothing, and block deeper layers, so the current winner's cost is genuinely
removed. Rows with a measured cost of 0 are excluded ("save ~0" is not useful). Cursor
never produces prune rows (no usage adapter); with `--prune` it prints an explicit
"usage unavailable" line rather than an empty block.

### Table verdict text

The unconditional `prune -> save ~N/session` is now provenance-aware: clean `suggestion`
rows keep `prune -> save ~N/session`; `candidate` rows show `prune candidate` so no
savings number is asserted without its caveats.

### `--prune` output

- Text: appended after the normal coverage and tables (the evidence stays with the advice)
  — a "Suggested removals" section and a separate "Prune candidates -- review" section,
  plain ASCII, each line naming the server, its scope, the file to edit, the estimate with
  its error band, and every caveat. A footer repeats that mcp-top never edits configs.
- JSON: `suggested_removals` is added under each `clis[]` entry (nested, alongside its
  coverage). Schema stays `mcp-top/v2` — all additions are backward-compatible fields
  (`coverage.unmatched_enabled_tools`, and `suggested_removals` only with `--prune`); no
  existing field is renamed, retyped, or removed. Both shapes are pinned by tests.

A same-name Codex project-layer entry (or a project layer that exists but cannot be read)
downgrades the corresponding user-scope prune to a candidate: a trusted project could
redefine that server, so removing the user entry may not save its full cost. The project
layer is still never queried, merged, or shadowed — only its *names* inform the caveat.

### Codex project layer — conditional inventory only

`<project>/.codex/config.toml` is now read and its server names listed in coverage, but it
is **not queried and does not shadow user servers.** Codex applies project layers only to
*trusted* projects (a state mcp-top cannot observe from files), reads multiple files from
project root down to cwd, and field-merges tables — so faithfully reproducing per-server
precedence from the spec is not possible. Per the honesty doctrine this ambiguity is
reported, not guessed. No `--codex-project-trusted` opt-in in v0.3.

### `enabled_tools` hardening (accepted item + a fix)

- After a complete successful `tools/list`, names in `enabled_tools` that were not returned
  by that snapshot are surfaced (phrased as "not returned by this tools/list snapshot", not
  an absolute claim), carried structurally on `ServerTools` and `Coverage`.
- A malformed `enabled_tools`/`disabled_tools` (present but not a list) previously became an
  empty allowlist that silently hid every tool and produced a misleading zero-cost prune
  row. It now warns and applies no filter.
