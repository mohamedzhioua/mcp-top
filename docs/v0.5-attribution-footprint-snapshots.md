## Why

v0.4 made the advertised/upfront/regime story honest for the Tool-Search era but
left three admitted gaps, all recorded in the joint Fable+gpt-5.6-sol roadmap:

1. **Prune verdicts are project-blind.** Usage is counted home-wide, so a
   user-scope server with 0 calls *in the current project* can still be flagged
   or, worse, its 0 count silently mixes sessions from unrelated projects
   (`engine.py:285-290` says so out loud). Codex rollouts already carry `cwd`
   in `session_meta`; mcp-top throws it away. Claude encodes the project in the
   transcript path slug and never uses it. This is a correctness hole, not a
   feature request.
2. **We report what servers *advertise* but never what *results* cost.** A tool
   that is cheap to advertise can return huge payloads every call. We have the
   recorded results in the transcripts (Claude `tool_result`, Codex
   `function_call_output`) and never look at them.
3. **No way to track footprint over time.** There is no artifact a user can
   commit, share, or diff to see "did pruning actually shrink my advertised
   surface / change my usage".

Plus one deferred-from-v0.4 refinement (sol's item): **Claude loading regimes**
are derived only from documented, locally observable settings signals. The
final Batch 3 scope deliberately excludes client-version inference because the
current docs say Tool Search is deferred by default but do not document the
version where that became true.

v0.5 is the **real launch** (v0.4 was a soft launch to collect compat
fixtures). Scope is fixed by the approved roadmap; this doc turns it into
batches with a verification bar.

## Non-negotiable honesty invariants (carried from v0.3/v0.4, extended)

- Estimates stay `~`-tagged; unknowns stay loud and first-class.
- **Recorded-result footprint is a LOWER BOUND on recorded bytes only.** It MUST
  be labeled "recorded result footprint" everywhere and MUST NOT be described as
  actual context cost, prompt tokens, billing, savings, or "what the model saw".
  A grep gate enforces the forbidden vocabulary on the live surface.
- Snapshots/diffs **never persist raw config** (no `env`/`args`/`command`/`url`)
  and **never persist result content** â€” only aggregate numbers and
  already-safe identifiers already present in v3 output.
- Regime refinement never fingerprints a remote; it uses only locally observable
  signals and stays `unknown` when evidence is incomplete.
- mcp-top remains strictly read-only: it never launches a process it does not
  already launch today, never writes user config, and (new subcommands) writes
  only the snapshot file the user names.

### Batch 1 â€” Project-filtered usage windows + prune-verdict honesty fix

- `count_calls` gains an optional `project_filter: str | None`. When set, only
  sessions whose `project` matches are counted; sessions with `project = None`
  are excluded from the filtered count **and** reported as unattributable.
- `UsageWindow` records attribution facts: `sessions_with_project`,
  `sessions_unattributed`, and (always, regardless of filter) a per-project call
  breakdown for each server so the report can say "0 here / N elsewhere".
- New flag `--project-usage`: filter usage to the current `--project`. **Default
  stays home-wide** (every project) so existing numbers and goldens are stable;
  this is opt-in. (See "Decisions for the gate" â€” default vs opt-in is a fork.)
- Engine prune logic uses attribution:
  - The v0.4 blanket candidate reason "usage is not attributed per-project" is
    **replaced** by attribution-aware wording. With `--project-usage`, a
    user-scope 0-call server whose per-project breakdown shows 0 here / >0
    elsewhere is called out precisely; 0 everywhere strengthens (not fabricates)
    the suggestion.
  - When attribution is incomplete (unattributed sessions exist), the reason
    stays loud and the row stays a candidate.
- Coverage gains an attribution line: sessions attributed vs unattributable, and
  whether a project filter is active.
- Tests: filtered vs unfiltered counts; unattributed exclusion; per-project
  breakdown; prune reason wording under each attribution state; default output

### Batch 2 â€” Recorded-result footprint

- Adapters capture result payloads and pair them to calls by id:
  - **Claude**: `tool_result` blocks in `user` records â†’ pair by `tool_use_id`.
  - **Codex**: `function_call_output` response_items â†’ pair by `call_id`.
- Per result, record observed inline bytes plus a completeness classification:
  `paired` (matched a call; entire content was inline text and measured),
  `partial` (matched a call; inline text bytes were measured but non-text or
  opaque parts were also present), `unsupported` (matched a call but the content
  shape had no measurable inline text), and `unmeasurable` (matched a call but
  UTF-8 byte measurement failed, e.g. a malformed lone surrogate). Results with
  no matching call are counted separately as unpaired results; MCP calls in the
  window with no paired result are counted separately as unpaired calls. Never
  retain result content itself.
- Aggregate per server (MCP calls only): recorded-result footprint as
  `recorded UTF-8 bytes -> ~bytes/4 tokens` **lower bound on recorded bytes**,
  with `total_bytes`, `total_tokens`, `max_tokens`, `p50_tokens`, and
  `p90_tokens` across that server's measurable `paired`/`partial` results.
  `unsupported` and `unmeasurable` results contribute 0 bytes and stay visible
  in coverage. `~`-tagged, labeled "recorded result footprint".
- JSON server footprint objects carry the lower-bound basis explicitly:
  `lower_bound: true`, `basis: "recorded_utf8_bytes"`, and
  `token_estimate: "bytes/4"`, plus the token objects and `total_bytes`.
- Surface in human table (a new column or a per-server line â€” see gate),
  `--json` (additive fields on the server object + a nullable coverage
  `recorded_results` summary), and coverage (`paired`/`partial`/`unsupported`/
  `unmeasurable`/unpaired-result/unpaired-call counts when a transcript window
  exists, otherwise `recorded_results: null`).
- Hard guard: a test asserts the forbidden vocabulary ("context cost", "prompt
  tokens", "billing", "savings", "what the model saw") never appears near the
  footprint label on the live surface.
- Tests: pairing by id on both adapters; byteâ†’token lower-bound math; each
  classification; percentile math; label/vocabulary guard; zero-result server.

### Batch 3 â€” Claude loading-regime refinement from observable signals

- Final scope: refine only from documented Claude Code settings signals that are
  locally observable in the existing settings layers. No remote calls, no
  fingerprinting, and no installed-version read.
- No version-based inference. Current MCP docs assert Tool Search is enabled by
  default but provide no documented version threshold for "deferred by default";
  the only versioned changelog fact reviewed for this batch, v2.1.7, describes a
  different `auto` threshold default. Therefore `unknown` remains the honest
  default when no local signal resolves the regime.
- Implement the explicit precedence ladder:
  - Tier 0 hard override: `env.CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`
    forces `upfront`.
  - Tier 1 explicit intent: `env.ENABLE_TOOL_SEARCH=true` forces `deferred`;
    `false` forces `upfront`; `auto` / `auto:N` stay `unknown` with threshold
    mode evidence. This tier overrides soft provider defaults.
  - Tier 2 soft provider defaults, only when `ENABLE_TOOL_SEARCH` is unset:
    non-first-party `env.ANTHROPIC_BASE_URL` forces `upfront`; documented Vertex
    selection `env.CLAUDE_CODE_USE_VERTEX=1` also forces `upfront`.
  - Tier 3 `permissions.deny=["ToolSearch"]` forces `upfront` because the
    discovery tool is denied. If paired with explicit `ENABLE_TOOL_SEARCH=true`,
    report `unknown` with contradiction evidence naming both settings.
- Keep scoped `ToolSearch(...)` deny rules as `unknown`; the docs document the
  deny syntax but do not define an exact whole-regime consequence for scoped
  denial.
- Per-server `alwaysLoad:true` and tool `_meta["anthropic/alwaysLoad"]=true`
  remain the only always-load markers. No new markers are modeled.
- Model support is documented as a factor for Tool Search (`tool_reference`
  support), including provider-specific model support on Vertex. mcp-top does
  not encode a model allow/deny list because it would rot across model releases
  and could misclassify future models.
- Tests: `ENABLE_TOOL_SEARCH` over soft base URL and Vertex defaults; hard beta
  disable over explicit enable; `auto` / `auto:N` threshold evidence; exact
  `ToolSearch` denial; explicit-enable/deny contradiction; existing
  settings-precedence and always-load behavior remains green.

## JSON schema decision (recommendation â€” confirm at gate)

Keep the schema string **`mcp-top/v3`** and add fields *additively*:
recorded-result footprint object on each server row + a coverage summary; an
attribution summary on `window`/`coverage`. Rationale: v0.4 just hard-broke to
v3 and the beta explicitly solicits v3 compat fixtures; a second break weeks
later burns that goodwill, and every v0.5 report addition is backward-compatible
(new keys only). `--project-usage` is opt-in, so default v3 output stays
byte-stable. Snapshots use a **separate** id `mcp-top-snapshot/v1` (new artifact,
new contract). A v4 break is only forced if project-filtered usage becomes the
*default* â€” which this spec recommends against.
