# v0.5 — Per-project attribution, recorded-result footprint, snapshots/diff

Status: APPROVED 2026-07-18 — all four gate decisions confirmed as recommended
(opt-in `--project-usage`; additive `mcp-top/v3`; per-server footprint line;
conservative regime refinement). Execution in batches on `feat/v05-*`.

## Why

v0.4 made the advertised/upfront/regime story honest for the Tool-Search era but
left three admitted gaps, all recorded in the joint Fable+gpt-5.6-sol roadmap:

1. **Prune verdicts are project-blind.** Usage is counted home-wide, so a
   user-scope server with 0 calls *in the current project* can still be flagged
   or, worse, its 0 count silently mixes sessions from unrelated projects
   (`engine.py:285-290` says so out loud). Codex rollouts already carry `cwd`
   in `session_meta`; mcp-top throws it away. Claude encodes the project in the
   transcript path slug and never uses it. This is a correctness hole, not a
   feature request.
2. **We report what servers *advertise* but never what *results* cost.** A tool
   that is cheap to advertise can return huge payloads every call. We have the
   recorded results in the transcripts (Claude `tool_result`, Codex
   `function_call_output`) and never look at them.
3. **No way to track footprint over time.** There is no artifact a user can
   commit, share, or diff to see "did pruning actually shrink my advertised
   surface / change my usage".

Plus one deferred-from-v0.4 refinement (sol's item): **Claude loading regimes**
are derived only from settings files; observable client-version / provider /
model signals could sharpen `unknown` → `deferred`/`upfront` without
fingerprinting.

v0.5 is the **real launch** (v0.4 was a soft launch to collect compat
fixtures). Scope is fixed by the approved roadmap; this doc turns it into
batches with a verification bar.

## Non-negotiable honesty invariants (carried from v0.3/v0.4, extended)

- Estimates stay `~`-tagged; unknowns stay loud and first-class.
- **Recorded-result footprint is a LOWER BOUND on recorded bytes only.** It MUST
  be labeled "recorded result footprint" everywhere and MUST NOT be described as
  actual context cost, prompt tokens, billing, savings, or "what the model saw".
  A grep gate enforces the forbidden vocabulary on the live surface.
- Snapshots/diffs **never persist raw config** (no `env`/`args`/`command`/`url`)
  and **never persist result content** — only aggregate numbers and
  already-safe identifiers already present in v3 output.
- Regime refinement never fingerprints a remote; it uses only locally observable
  signals and stays `unknown` when evidence is incomplete.
- mcp-top remains strictly read-only: it never launches a process it does not
  already launch today, never writes user config, and (new subcommands) writes
  only the snapshot file the user names.

## Scope — IN

### Batch 0 — Project identity in the session model (foundation, no behavior change)

- Add `project: str | None` (a normalized project key) and `raw_cwd: str | None`
  to `SessionResult`. Populated but unused by reporting in this batch.
- **Codex**: read `payload.cwd` from the `session_meta` record; normalize to the
  project key. (`adapters/codex.py` already parses `session_meta`; add the field.)
- **Claude**: derive project identity from the transcript path slug that
  `session_key` already isolates (`~/.claude/projects/<slug>/…`). The slug is a
  lossy encoding of the absolute cwd (separators/`.`/`_` → `-`). Provide a
  best-effort slug→project-key mapping AND keep the raw slug; when the slug
  cannot be mapped unambiguously to the `--project` path, the session is
  `project = None` (honest "unattributable"), never a wrong guess. The exact
  Claude slug scheme MUST be verified against a real `~/.claude/projects`
  directory on this machine before locking the mapping — do not trust this
  spec's description of the encoding.
- One shared `normalize_project_key(path)` helper (case-fold on Windows, strip
  trailing sep, `os.path.normpath`) reused by both adapters and the CLI
  `--project` value, so matching is apples-to-apples.
- Tests: Codex cwd populated from fixture; Claude slug parsed from a fixture
  path; normalization idempotence; unmappable slug → `None`.

### Batch 1 — Project-filtered usage windows + prune-verdict honesty fix

- `count_calls` gains an optional `project_filter: str | None`. When set, only
  sessions whose `project` matches are counted; sessions with `project = None`
  are excluded from the filtered count **and** reported as unattributable.
- `UsageWindow` records attribution facts: `sessions_with_project`,
  `sessions_unattributed`, and (always, regardless of filter) a per-project call
  breakdown for each server so the report can say "0 here / N elsewhere".
- New flag `--project-usage`: filter usage to the current `--project`. **Default
  stays home-wide** (every project) so existing numbers and goldens are stable;
  this is opt-in. (See "Decisions for the gate" — default vs opt-in is a fork.)
- Engine prune logic uses attribution:
  - The v0.4 blanket candidate reason "usage is not attributed per-project" is
    **replaced** by attribution-aware wording. With `--project-usage`, a
    user-scope 0-call server whose per-project breakdown shows 0 here / >0
    elsewhere is called out precisely; 0 everywhere strengthens (not fabricates)
    the suggestion.
  - When attribution is incomplete (unattributed sessions exist), the reason
    stays loud and the row stays a candidate.
- Coverage gains an attribution line: sessions attributed vs unattributable, and
  whether a project filter is active.
- Tests: filtered vs unfiltered counts; unattributed exclusion; per-project
  breakdown; prune reason wording under each attribution state; default output
  byte-identical to v0.4 goldens (no `--project-usage`).

### Batch 2 — Recorded-result footprint

- Adapters capture result payloads and pair them to calls by id:
  - **Claude**: `tool_result` blocks in `user` records → pair by `tool_use_id`.
  - **Codex**: `function_call_output` response_items → pair by `call_id`.
- Per paired result, record **recorded UTF-8 byte length** of the result content
  and classify: `paired` (matched a call), `unpaired` (result with no matching
  call, or call with no result), `truncated` (transcript marks the payload
  truncated), `externalized` (content is a file/pointer reference, not inline
  bytes). Never retain the content itself.
- Aggregate per server (MCP calls only): recorded-result footprint as
  `bytes → ~bytes/4 tokens` **lower bound**, with `total`, `max`, and
  percentiles (p50/p90/p100) across that server's calls. `~`-tagged, labeled
  "recorded result footprint (lower bound)".
- Surface in human table (a new column or a per-server line — see gate),
  `--json` (additive fields on the server object + a coverage summary), and
  coverage (`paired`/`unpaired`/`truncated`/`externalized` counts).
- Hard guard: a test asserts the forbidden vocabulary ("context cost", "prompt
  tokens", "billing", "savings", "what the model saw") never appears near the
  footprint label on the live surface.
- Tests: pairing by id on both adapters; byte→token lower-bound math; each
  classification; percentile math; label/vocabulary guard; zero-result server.

### Batch 3 — Claude loading-regime refinement from observable signals

- Extend regime resolution to consider locally observable signals beyond
  settings files: the **client version** actually observed in Claude transcripts
  (the `version` field the adapter already reads) and any locally observable
  provider/model signal, used only to move `unknown` → `deferred`/`upfront`
  when the signal is documented and unambiguous.
- Keep `unknown` + ranges whenever evidence is incomplete; every refinement adds
  an `evidence` entry naming its source. No remote calls, no fingerprinting.
- This crosses the adapter↔config seam (version lives in transcripts, regime is
  computed in `config.py`). Introduce a narrow, explicit input — an observed
  `client_versions` set threaded from the CLI into regime resolution — rather
  than coupling the two modules. The exact version→behavior mapping and any
  provider/model keys MUST be verified against current Claude Code docs before
  implementation (same rule v0.4 used for settings keys).
- Tests: version signal moves `unknown`→resolved with evidence; incomplete
  evidence stays `unknown`; no regression to settings-derived regimes;
  evidence provenance strings.

### Batch 4 — Redacted aggregate snapshots + semantic diff

- New subcommands via argparse subparsers; **the default (no subcommand)
  invocation preserves today's behavior and output byte-for-byte**:
  - `mcp-top snapshot [--out FILE]` — emit a redacted aggregate snapshot
    (schema `mcp-top-snapshot/v1`): advertised footprint, loading bounds
    (floor/max), loading regime, usage counts + attribution summary, and
    recorded-result footprint aggregates. No raw config, no result content, no
    secrets. Timestamped; deterministic ordering.
  - `mcp-top diff OLD NEW` — semantic diff of two snapshots: per-server deltas in
    advertised max / upfront floor / regime / usage / recorded-result footprint,
    plus added/removed servers. Human + `--json`.
- Redaction is enforced structurally (snapshot is built from already-safe report
  fields, never from `ServerConfig`), with a test that no snapshot field can
  carry `env`/`args`/`command`/`url`/result content.
- Tests: snapshot schema golden; redaction guard; diff of two fixtures (add,
  remove, grow, shrink, regime change, no-change); malformed/mismatched-schema
  snapshot handled with a clear error, not a traceback.

## Scope — OUT (explicitly, per roadmap)

- Cursor SQLite usage adapter, tokenizer dependency, npm shim, Gemini adapter,
  Streamable HTTP, CI coverage thresholds. All v1.0 or rejected.

## JSON schema decision (recommendation — confirm at gate)

Keep the schema string **`mcp-top/v3`** and add fields *additively*:
recorded-result footprint object on each server row + a coverage summary; an
attribution summary on `window`/`coverage`. Rationale: v0.4 just hard-broke to
v3 and the beta explicitly solicits v3 compat fixtures; a second break weeks
later burns that goodwill, and every v0.5 report addition is backward-compatible
(new keys only). `--project-usage` is opt-in, so default v3 output stays
byte-stable. Snapshots use a **separate** id `mcp-top-snapshot/v1` (new artifact,
new contract). A v4 break is only forced if project-filtered usage becomes the
*default* — which this spec recommends against.

## Decisions for the gate (User-Challenge — I need your call)

1. **Project-usage default.** Recommend **opt-in `--project-usage`**, default
   stays home-wide (stable numbers, least surprise, additive schema). Alternative:
   make project-filtering the default (more "correct" per-project, but a
   semantic break → forces v4 and changes every existing number). → *My call:
   opt-in.*
2. **JSON schema.** Recommend **additive `mcp-top/v3`** (above). Alternative: v4
   hard break. → *My call: additive v3.*
3. **Footprint in the human table.** Recommend a **per-server line** under the
   table (keeps the 7-column table readable; footprint is secondary to
   advertised/upfront). Alternative: an 8th column (denser, risks width blowout
   on narrow terminals). → *My call: per-server line.*
4. **Regime refinement aggressiveness (Batch 3).** Recommend **conservative**:
   only documented, unambiguous version/provider signals flip `unknown`;
   anything else stays `unknown`. This is the item sol deferred precisely because
   it is subtle. → *My call: conservative, honesty-first.*
